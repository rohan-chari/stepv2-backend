# Event traffic efficiency — requirements

Status: **Implementation approved by the user; architect approved with no remaining required changes. Implementation and validation in progress; production deployment requires separate approval.**
Date: 2026-09-09
Owners after approval: backend-developer (API, intake, workers), frontend-developer (Flutter consumption and rendered behavior). Architect review follows initial user approval, per the repository AGENTS.md workflow; required design changes must be incorporated before implementation.

## 1. Summary and user story

During daily events, users legitimately open the app, upload steps and inspect races more often. Reduce the database work generated by each action while preserving durable step intake, accurate race totals and timely visible updates. Do not meet the goal by reducing accepted activity, increasing polling intervals, postponing required scoring, or adding infrastructure.

As a participant, I can open Home, sync and inspect updated races during an event with the same information and correctness as today, while the service performs fewer repeated reads and unchanged writes.

Evidence: [action investigation](event-action-efficiency-2026-09-09.md), [measurements](evidence/event-action-efficiency-2026-09-09.json), [managed CPU investigation](db-cpu-eastern-event-2026-09-09.md).

Measured local reference: unchanged fresh-key sync 15 observed SQL events; changed one-sample sync 16; post-resolution Home/races/profile reads 14 + 11 + 1 events. These are scenario-specific Prisma events, not universal physical round trips. Production census: 895/946 users with unfinished active memberships belong to multiple races. The 293-event worker startup/drain measurement is **not** an incremental per-action baseline.

## 2. Scope and non-goals

This release contains three independently testable workstreams:

A. Add an opt-in Home catch-up response that refreshes existing core Home information without reloading equipment/cape and friendship presentation. Use it only following successful race-resolution polling when this account already has a complete Home shell.

B. Remove an unchanged scoring-state write and consolidate the unchanged daily-row read where serialization proves safe. Preserve the repeated negative summary-work lookup for now: concurrent event-end insertion makes its removal a separate correctness decision.

C. Coalesce compatible concurrent worker source-input loads, using the existing source-generation and coverage guards. Share immutable step/sample inputs only; each race keeps its own scoring computation and commit validation.

Out of scope: scoring/economy changes; new rewards; removal of either scoring fingerprint validation; dropping required jobs/notifications; snapshot repair redesign; operational-counter changes; additional named-prepared-query rollout; notification-history scan redesign; new global caches; new polling delays; production capacity changes. Larger opportunities remain documented in the investigation and are not silently bundled into this release.

No new feature flags, rollout switches, runtime controls or environment settings. The explicit HTTP response representation below is a permanent versioned API contract, not a release flag.

## 3. Invariants

- Every accepted upload retains immutable idempotency response, canonical sample durability, source generation/queue ownership, summary capture coverage and the successful-sync timestamp.
- Same-key replay, conflicting-key rejection, Home cooldown and legacy `/steps` plus `/steps/samples` semantics remain unchanged.
- A time-boundary crossing, source correction or ownership repair must still trigger work even if the submitted daily number is unchanged.
- Post-resolution refresh continues to update the race list and profile. Coins, new results, milestone/reward state, event summary receipts and unread state must not become stale because this release saved an unrelated read.
- Frozen apps receive their existing responses and benefit from safe backend reductions without updating.
- iOS and Android use the same Flutter behavior. Account changes and out-of-order responses cannot apply one account's data to another.

## 4. API contract

### New optional representation on an existing endpoint

`GET /home/race-card?view=sync-refresh-v1&homeActiveRaces=1&localDate=YYYY-MM-DD`

Existing authentication, timezone, release-channel and client-capability headers apply. Optional `homePersistedTotals=1` retains its current meaning and must not be set merely because intake returned 202. No new required parameter is added to an existing request form.

Successful response, HTTP 200:

```json
{
  "contract": "home-sync-refresh-v1",
  "home": {},
  "retainedSections": ["presentation", "friends"]
}
```

`home` is the complete existing core Home response object produced by `buildHomeRaceCardResponse`, with only the shell-envelope fields `contract`, `resolved`, `presentation` and `friends` omitted. Validation requires `home` to be an object containing string `state` and object `data`. Allowed states: EMPTY (an empty data object is valid), ACTIVE_RACES (data.races is a list of objects with nonempty raceId), ACTIVE_RACE (nonempty data.raceId, nullable object me/leader, object-list others), PENDING_INVITE/PUBLIC_RACE (nonempty data.raceId), FRIEND_RACING (nonempty data.raceId, object friend, object-list participants), FRIEND_FINISHED (object friend and string raceName). Unknown states, missing required fields or invalid containers reject the narrow response and use the defined full-shell fallback; optional fields remain defensively parsed. Backend fixtures must pin each state against current output before business logic.

Its field names, nullability, client-capability filtering and optional-section failure behavior are exactly those of the existing Home assembler. `{}` above illustrates the envelope, not a valid complete production Home payload. Implementation must capture a populated real-HTTP shell response fixture and prove the `home` object matches that shell after removing exactly those four keys. No new nested business schema is introduced.

`retainedSections` is the exact array shown. It explicitly tells the consumer to retain previously loaded presentation and friendship data; omitted sections must not be interpreted as empty or failed. This release introduces no additional retained section.

The narrow assembler **must skip executing** `getHomeShellPresentation` and `getFriendsSummary`; constructing and then deleting their results does not satisfy the requirement. All other Home computations retain current semantics, including optional failure handling and event-summary freshness. The response contains no new authoritative coin field: the existing profile refresh remains responsible for its current coin/balance refresh behavior, and cached presentation cannot overwrite newer coins.

Existing `view=shell-v1`, absent view, and all other existing representations remain byte-shape compatible (ignoring timestamps/normal transient data). The new view is routed to the shared assembler explicitly; it must not depend on the historical parallel-optional setting choosing a particular branch.

Errors: preserve existing 401/403 authorization and existing 500 behavior for fatal Home assembly failure. Optional sections retain their current failure/default contract. Do not return HTTP 200 with an incomplete required core object.

### Old server / invalid response behavior

An old server may return HTTP 200 with a legacy Home response for the unknown view. The app accepts a narrow response only if its discriminator, object shape and retained-sections contract validate. Otherwise it requests the ordinary shell once, using the existing full-shell application path. HTTP 404/405 also use that fallback once. Network failure/5xx keeps the last coherent Home state and uses existing error/retry behavior; it must not trigger a second immediate load during overload.

Unsupported representation is remembered only within the authenticated app session, scoped to backend origin. Clear on account/backend change; a new launch may retry support. This is client protocol negotiation, not a remotely configurable toggle.

All other endpoints and error bodies are unchanged. No rate-limit or polling-frequency change.

## 5. Frontend implementation

Primary files: `lib/services/backend_api_service.dart` near `fetchHomeRaceCard` (2165); `lib/screens/main_shell.dart` near `_startJobPolling` (2257), `_loadHomeAndShowResultsInner` (2722), `_fetchRaceCard` (3706). Line numbers are investigation anchors and may move.

1. Add a typed result/parser for the new representation and a service method using the existing HTTP/auth surface. Do not add networking to a widget.
2. Separate common core-Home response application from full-shell presentation/friends application. Full-shell behavior remains unchanged. A narrow response replaces the entire core Home object and retains only the explicitly named two sections; do not shallow-merge arbitrary old optional fields, which would preserve expired summaries or banners.
3. Use narrow refresh only in the successful resolution-status callback, after a full shell has resolved presentation and friends for the current account. If either is unresolved or no full shell exists, call the existing full-shell method. Both retained sections must come from a full shell accepted within the existing 60-second friends freshness window, with no subsequent equipment/friendship mutation or invalidation; otherwise use the full shell. Track their original successful fetch time and never renew it when retaining data. Expose a monotonic invalidation revision from FriendsSummaryRepository covering every existing invalidate/clear mutation seam; observe it in MainShell rather than the currently empty onFriendsChanged callback. Use equivalent revisions for _onShopCatalogChanged/equipment changes and account identity. Capture revisions when a full-shell request starts; retention is valid only if unchanged at acceptance and again at narrow completion. An invalidation during an in-flight narrow refresh schedules one full-shell refresh and prevents stale retained sections from being applied. This permits brief reuse of already-fresh presentation, not indefinite suppression of friendship/equipment updates.
4. Continue `_fetchRacesCore()` and `_refreshMe()`. Do not change their sequencing, authorization or results-modal requirements. Do not reapply stale retained `presentation.coins` through `_applyShopCatalog` when merging a narrow response. Coins from the profile refresh must continue to reach the existing balance UI.
5. Retain current generation/auth guards and loading behavior. A full request started before job completion is not proof of post-completion freshness. A late full response must not overwrite a later accepted narrow response, and vice versa; use one monotonically increasing Home response generation.
6. Coalesce only concurrent catch-up refreshes for the same account whose fetch began after the required completion observation. If a newer completion arrives during an older fetch, mark one additional refresh pending; do not attach it to an already-stale request. No new debounce delay.
7. Keep cold open, deliberate Home pull, event-summary-triggered Home refresh and normal navigation on the existing full path. If summary and job refresh overlap, preserve current overlay precedence and the independently received summary receipt.
8. Demo/test subclasses must not fall through to live networking. Follow the existing subclass/unsupported convention; fakes may opt into the new typed method or exercise the legacy fallback.

There are no widget additions, removals, moves, text changes or styling changes. Loading, empty, permission-denied and error presentation stay unchanged. A placement checklist is not applicable; real-screen data/freshness checks are required on both platforms and tutorial/demo paths that instantiate MainShell.

## 6. Backend intake implementation

Files: `src/modules/steps/services/stepInputIntake.js:72`, `scoringInputVersion.js:197`; callers in `commands/recordStepSyncV2.js` and legacy intake commands; relevant SQL migrations/triggers and timestamp consumers.

### Unchanged scoring state

Before editing, audit every reader of `user_scoring_input_versions.updated_at` and every trigger attached to that table. Preserve any externally required semantics. Compare the already-locked state with the exact proposed generation, watermark, next boundary and queue-ownership generation. If all are identical and the row is already materialized, omit the UPDATE. Null-safe comparisons are mandatory. Creation, crossing a future sample boundary, watermark repair and queue-generation repair still write. Never omit a required write merely because incoming `steps` is unchanged.

If updated_at is used as an upload heartbeat, keep its existing semantics and report the resulting blocker rather than repurposing it; the project must not claim the no-op-write saving until this audit and tests establish it. Do not add a schema field just to recover the metric.

### Daily-row response in one statement

Keep the existing source-row lock ahead of daily persistence. Extend the existing CTE so either the changed row from INSERT/UPDATE or the unchanged stored row supplies the response. The existing fallback SELECT remains only for a real concurrent snapshot-visibility race, if one is reachable through a legacy writer. Audit all daily writers before removing that fallback entirely. Under normal serialized unchanged intake there must be no second SELECT.

Preserve existing `existed`, `storageChanged`, id, date and compatibility stepGoal semantics. Do not replace a suppressed UPDATE with a dummy UPDATE solely to obtain RETURNING. Do not add new locking to shared event/race rows to save this read.

The active-summary negative recheck remains unchanged in this release. The illustrative no-op target is therefore **15 to at most 13 comparable observed SQL events**, not the earlier three-candidate ceiling of 12. Correctness takes precedence over this target, and a failed proof blocks the relevant optimization rather than silently changing behavior.

## 7. Worker source-load coalescing

Files: `src/modules/races/services/raceScoringPrefetch.js:20,470,765`, `src/modules/steps/models/stepSample.js:142`, plus existing source-cache tests and real resolution-entrypoint observers.

Add a process-local pending-load registry beside the existing completed source-input cache. The key must include datasource/model identity, user ID, canonical source generation, sample coverage bounds and daily coverage bounds. Start with **exact compatible coverage only**; do not widen source ranges to force hits. Completed-cache hits must use the same datasource/model namespace; the existing user-only completed cache must not bypass this isolation. Preserve bulk loading for unrelated users. Include any other existing cache eligibility discriminator discovered at the call site.

- Only source reads outside transaction-local snapshots are eligible. Never reuse a Promise/result between transactions or datasource instances, or hold another transaction's locks while awaiting a shared read.
- Same compatible key concurrently requested shares one load; different generation, user, range, model or datasource performs an independent load.
- Completed immutable input remains governed by the existing bounded cache and expiry rules. A source-generation change invalidates reuse; commit fingerprints remain authoritative.
- Never share scratch-file-backed/paged timelines, cursor ownership, mutable scoring models, per-race accumulators or disposable timeline ownership. If the leader discovers paging while loading, it retains exclusive ownership and signals waiters to perform their own existing bounded loads; it must not publish a paged result, scratch buffers or cursor to them. Include memory/row/loading budget discriminators in sharing eligibility. Start with the in-memory immutable representation already accepted by the completed cache. Callers must not mutate shared data.
- Bound pending entries by the existing cache user budget. At the bound, use the current bounded loading path; never introduce unbounded queues or concurrency. Pending entries are removed on fulfillment or rejection; failures do not poison later requests. A joining caller cancelling must not cancel work still owned by another caller.
- On failed shared read, propagate the normal read failure to its current waiters and let the existing worker retry policy act. Do not multiply immediate retries per waiter. Preserve cleanup on shutdown.
- Do not add TTL-based reuse across source generations, remove either fingerprint, reuse event/effect decisions across races, or change prepared-plan settings.

Controlled acceptance: three overlapping compatible requests for a nonempty, one-page immutable source range produce one physical source SELECT instead of three; an unchanged empty result is also shared. This target is for a new deterministic overlap fixture, not a claim that all earlier production sample reads were duplicates. Establish and retain an unmodified warm-worker baseline before implementation.

| App | Backend | Behavior |

| New app | New backend | Full initial Home; narrow eligible post-job refresh |

## 11. Performance acceptance and definition of done

Produce matched baseline/candidate evidence with identical fixtures, code configuration, cache conditions, traffic trace and worker limits. Separate SQL SELECT/INSERT/UPDATE/DELETE/control calls, actual row versions changed, planning/execution elapsed, queued/coalesced/completed jobs and time to user-visible freshness. Trigger work and idle worker overhead must be accounted for separately where observable.

- Qualifying unchanged intake saves the normal daily fallback read and scoring-state UPDATE (two statements, at least one avoided row version) without losing required durability. The comparable 15-event fixture target is <=13; measure on the exact implementation, not by subtracting unrelated counters.
- Narrow Home sends zero equipment/cape or friendship-presentation reads attributable to those skipped services. Combined post-resolution Home + race-list + profile SQL must be strictly lower than its matched full-shell baseline; no savings target assumes removal of the latter two requests.
- Controlled identical concurrent source loads reduce three to one SELECT with identical final race results and no new writer stalls. Mixed incompatible work remains bounded.
- Define a deterministic event session trace before measuring: app open/upload, Home and race reads, completion poll and catch-up, plus start/end cohorts; cover 1, 3 and 5 race memberships and both same-race and disjoint-race concurrent users. Run at least three baseline and three candidate repetitions per trace at the same fixed offered arrival rate; report all runs, accepted throughput, completion counts and tails, not the best run. Fix the trace and acceptance thresholds before candidate measurements.
- At the same offered traffic, accepted throughput must not decrease and error rate or p95/p99 time-to-visible-results must not worsen beyond the baseline's repeat-to-repeat variation. If saturated locally, report the capacity boundary rather than changing the offered trace between versions.
- User objective remains approximately 70% average managed DB idle under comparable traffic; this release cannot promise it from query counts. After an authorized deploy, compare direct managed CPU with comparable real traffic, isolate steal/I/O wait, and do not attribute monitor-induced load to the app.
- All correctness tests pass; old-app/new-backend and new-app/old-backend behavior verified; reviewer has no unresolved required changes. Report any failed saving or incomplete load validation plainly. Specification completion is separate from implementation and production validation.
