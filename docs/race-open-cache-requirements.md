# Race detail opening: complete display caching

## Summary and authorization
Cache the remaining race-opening display inputs so repeated GETs reuse Redis and avoid repeated PostgreSQL work. The user approved the property-by-property caching proposal and explicitly authorized tests-first implementation and regression verification. Production deployment is not authorized by this task.

## Scope and API contract
Preserve every existing response and access/error contract on GET /races/:raceId/bootstrap, /races/:raceId and /races/:raceId/progress. No new parameters, required fields, client capabilities, flags, database migrations, or app release. Keep compact paged, legacy full, team, preview, spectator, pending and completed paths compatible. Cache domain inputs rather than final capability/privacy-filtered packets. Preserve consume-once mystery-box notifications outside cached packets.

Implement every property in the approved chart:
1. Race status and current core; viewer membership status and mute preferences.
2. Participant powerupSlots, nextBoxAtSteps, bonusSteps, maxBonusSteps and canonical boxProgressSteps. Derive stepsUntilNextPowerup without another database read.
3. Full participant summary: total/accepted/team counts, held pot, member IDs and all payout eligibility counts/arrays, shared within and across requests.
4. Raw active effects, filtered for current time and viewer on output.
5. Mystery-box preview eligibility inputs; derive dropOdds and dropOdds.reelPreviewAvailable with current balance configuration and truthful capabilities. No economic or scoring behavior changes.
6. Trail Mix distinct used type history.
7. Rematch and series state: rematchEligible, series.enabled, subscribed and canManage.

PostgreSQL remains authoritative for mutation eligibility, scoring, minting and settlement. Keep one narrow SQL access gate per request (existence/current visibility, direct membership, accepted tournament membership and seeded capability marker), reused by bootstrap details/progress. Membership/status display properties are cached, but cached state never grants private access or overrides fresh access/status transitions. The existing best-effort invalidation broadcast cannot prove revocation safety during a partial writer Redis failure. Redis-disabled/error/malformed/evicted paths fall back to SQL, never invented empty or unavailable business state.

### Full display compatibility cache
Legacy, null-timezone, and team GETs additionally reuse `race-open:roster:raceId` (30s, race-members + participant-display:race:raceId + participant-display:roster:raceId), carrying only the explicit RaceParticipant scalar allowlist above. Payloads over 512KiB or 10,000 rows remain uncached; clients retain their full original response. This is a DISPLAY-only method; workers/mutations continue to use uncached `findProgressScoringContext`. The narrow fresh access row always replaces/removes the viewer in a cached roster before any authorization check. Individual display writes invalidate this roster marker without invalidating race-members/list markers. Tests for all three paths failed first on full race/participant SQL (/tmp/race-open-roster-red.log).

Final writer audit additions: `seededRaceRenewal.activatePending` advances race scalar markers after the successful raw activation and precise participant markers for repaired box thresholds; `seededChallengeAdmission` advances race markers for bucket pointer/status updates and membership markers for create/reactivation. `completeRace.reconcileDurablePayoutArtifact` batches participant payout invalidation after its final raw payout overwrite. A warm public team-forfeit recovery test isolates that overwrite between PostgreSQL barriers; removing only its hook in an isolated runtime produces the expected stale payout failure.

The authoritative access SQL also selects `isTeamRace` and `teamSize`, preserving frozen-client compatibility during failed Redis invalidation. Core hydration finishes before that query so a resize during hydration is observed. Modern clients retain one gate; frozen clients additionally retain their original two-field compatibility preflight before the fresh handler gate, preserving resize concurrency behavior. When legacy progress reconciliation changes status within bootstrap, the handler rechecks authoritative access/compatibility and loads one fresh full result preload, discarding the previous request memo. This uncommon status-transition branch deliberately performs additional reads. Existing bootstrap reconciliation and frozen-client resize contract tests cover these branches.

Effect fragments depend on both `race-effects` (external scoring-input mutations) and `race-effects-display` (C0 effect row outputs). C0's own BLOCKED/EXPIRED/terminal-metadata writes advance only the display output marker; advancing the scoring-input marker there would invalidate the worker's original publication proof. Protected RUNNERS_HIGH/LEG_CRAMP expiry tests exposed this distinction.
