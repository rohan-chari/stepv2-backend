# Team races 10v10 API contract — locked for 2.3.13

The permanent binary capability is `team_races_10v10_v1` in `X-Client-Features`, alongside `team_races`. It is not a runtime flag.

- Existing create/edit shapes and statuses stay unchanged. Integer teamSize 1..10; maxParticipants is derived as twice teamSize. Unsupported clients attempting sizes 6..10 receive HTTP400 `{error: "Update the app to use this team race", code: "UPDATE_REQUIRED"}`. Invalid sizes remain HTTP400. Existing <=5 behavior stays compatible.
- Sizes >5 are filtered from incompatible public discovery, suggestions and invitation cards, with capability-separated caches. Already accepted members retain their pending/active/completed list cards and earned rewards/leave actions after downgrade. Direct reads/actions require the new request header. Downgraded members retain leave/forfeit, payout claim, results-seen and notification acknowledgement access; membership and money are never removed by filtering.
- Details and bootstrap `race` add `teamAcceptedParticipants`: all accepted members (including forfeited members), bounded at20, in the SAME privacy/cosmetics-safe participant shape as `participants`; and `teamRosterComplete:true`. Present only for new-capability team requests. Existing `participants` and its paging metadata continue to represent bounded invitation/history pages. New-capability team reads without page parameters default this history to the first50 rows; old callers preserve their prior behavior. Accepted roster is independent of page offset/limit and invitation count. Authoritative counts remain `acceptedCount`, `teamAAcceptedCount`, `teamBAcceptedCount`.
- New clients use `teamAcceptedParticipants` as accepted membership truth when `teamRosterComplete` is true; progress may overlay scoring/display fields by userId when its full accepted array is complete. A failed/partial progress read never replaces that roster. Missing marker/array on old server is an unavailable-completeness fallback, not proof of empty slots. Progress already returns full accepted teams and keeps its shape.
- Reuse the existing durable monotonic User.clientFeatures union, populated only from authenticated actual request headers. No migration or new endpoint. Deferred approval reads the requester's durable features independently, never copies the owner's header. All direct admissions still require the current device header, including downgrade.
- Enlargement above5 requires fresh bounded accepted-user capability reads under the race lock; all must have the token, including the creator. Reject HTTP400 UPDATE_REQUIRED without race/membership/money changes if any proof is absent. Members establish proof simply by using the updated app (existing authenticated metadata handshake). Bookkeeping is best-effort: persistence failure conservatively rejects enlargement/approval and can be retried; auth success is not inferred durable proof.
- Edit reads, compatibility/count validation and writes share the established race join transaction lock. Outstanding old invitations/requests never bypass new-size admission checks. Retried requests may refresh their own capability proof.
- Existing payout versions, scoring, equal-smaller-side starts, full-roster autostart/schedules and two-production-worker topology stay unchanged. No migration is needed; backend deploys before app. No runtime rollout control.

Shared helpers in `src/modules/races/teamRaces.js`: `TEAM_RACES_10V10_FEATURE`, `clientSupportsLargeTeamRaces(clientFeatures)`, `requiresLargeTeamSupport(race)`, `assertLargeTeamSupport(race, clientFeatures, ErrorClass)`. Read APIs accept optional `supportsLargeTeamRaces=false`; getRaces uses that options property. Cache variants include the permanent capability.

Architecture revision: existing authenticated sticky-union persistence was inspected and approved for historical support proof. Participant/request columns and explicit refresh endpoint were withdrawn before frontend implementation.
